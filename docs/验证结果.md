# 0.4.15 单/双 CPU 线程对照与低核选择

- 实验源码 `194df38` 的应用默认仍为双线程，nice 1 和原有采集/显示/分析截止不变。新增仅手动执行的 `Inference thread profile`：同一模拟器按 2→1→1→2 运行四次完整相机/模型/PiP，每次独立 instrumentation 进程，优先级固定 1；所有轮次执行，任何失败使诊断工作流失败。

# 0.4.13 停止后的定时任务

- 源码中预览 watchdog 无条件在回调末尾再次排队，onStart 也无条件启动，因此可见故障和返回后的停止页面仍以 100ms 周期运行。首页仅判断是否存在 Activity，因此保留已停止的预览时仍以 500ms 周期查询。

## 失败与后续检查

- [首次检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40867251405)的两套系统输入/模型对照均通过；Android 36 后续息屏恢复停在锁屏恢复页，探针仅等待 resumed 就点击恢复，未等待屏幕/锁屏状态。加强为屏幕关闭、离屏停止确认后再唤醒，并等待 interactive、解锁及 resumed，保留原应用锁屏保护和所有截止时间。
- [第二次检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40868016133)的 Android 36 在 PiP 探针报告 `Process crashed`；当时没有采集 crash buffer，没有取得堆栈，原因未确定。补充 crash、系统生命周期/进程日志和分阶段计时后，[诊断版](https://github.com/cyanrbt/walkbuddy/actions/runs/40868936484)未复现。一次成功不能证明此问题已修复；后续每套模拟器增加第二轮完整识别/PiP 流程，并保留两份探针文本与失败日志。
- [增加重复流程后的检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40869691616)在 Android 36 两轮 PiP 通过，Android 35 首次开启识别后触发截止，旧通用文案标为“采集/显示”。该次拒绝结果本身仅约 6.6ms 旧；尚无分析间隔日志，不能据此判断是哪一路心跳，crash buffer 为空。参考 [Android 线程调度指南](https://developer.android.com/topic/performance/threads)，在模型创建前将唯一推理 worker 设为后台线程优先级，并增加初始化、慢画面复制与心跳间隔日志。资源争用当时只是待核对的推断；原截止值保持不变。
- [线程调度后的检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40870945359)的 Android 35 仍在首次分析触发截止；新增日志显示采集/显示仅隔 58ms/25ms，实际超过的是分析截止，先前“采集/显示截止”的通用文案不准确，已改为“预览或分析截止”。模型先后初始化耗时 514ms 和 84ms，线程优先级确认是 10。源码中输入帧超过 1000ms 就关闭模型，会让仍有效的会话重复加载。改为仅保留同一有效 Ticket 的已就绪模型，旧帧/结果仍丢弃；进一步将准备模型与采样拆开，模型就绪后才取新帧。准备、重试和保留模型均不更新分析心跳，1500ms 原截止不变。前述资源争用不能作为已证实的唯一原因。
- [拆开模型准备后的检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40873194521)：Android 35 两轮通过，Android 36 第一轮通过，第二轮复现进程退出。这次 crash buffer 定位到主线程 `TextureView.draw` 的空 `TextureLayer`。对照 [AOSP Android 16 TextureView](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/core/java/android/view/TextureView.java)，绘制内部会调用帧更新监听，随后继续使用纹理层；原故障路径在监听内同步移除 View，重入销毁了该层。修复为遮挡/停止/取消立即执行，清空取景业务引用与监听，下一条主线程消息再 detach。源码也明确禁止在绘制中 getBitmap，因此亮度/采样改为最多一个延后读回任务，保留原帧时刻与 generation/epoch/View 身份，前后重验截止、关闭时取消。
- 新增实际硬件加速 TextureView 回归：在真实帧更新回调内部注入过期心跳并调用原监听，检查立即遮挡/资源释放、回调返回后移除旧 View、无崩溃且可手动恢复。它直接覆盖这条重入路径；先前没有堆栈的进程退出无法逐一追溯，不能断言全部与它同因。

- getBitmap 自己触发的更新不计为显示心跳，复制后再检查原 Ticket、generation、epoch、View 身份与帧龄。仅窗口几何变化时清掉旧帧/回调并增加 epoch，同一相机会话保留模型；关闭检测、停止和模式切换仍取消 Ticket 并关闭模型。新增两个阻塞回归，PiP 探针同时核对进入/展开前后的 Ticket 与模型对象相同。
- [批量 RGB 与几何复用检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40877112312)的 Android 35/36 均成功：每套两轮 PIP_PROBE_PASS、两次真实绘制截止恢复，以及输入/模型、布局、轮廓和权限恢复检查全过，模型保留断言已执行。
- [之前一次首包失败](https://github.com/cyanrbt/walkbuddy/actions/runs/40876140236)发生在开启检测之前。时间日志显示采集心跳仍为 0，元数据年龄约 1.449 秒，是启动阶段的旧包。现在仅在 STARTING 丢弃旧包，不记录采集心跳、不晋升 LIVE、不记录预览成功；保持遮挡并等待新鲜采集/显示，原始 5000ms 启动截止不延长。LIVE 中旧戳仍立即失败。两项新增回归验证只有新鲜结果能完成启动、反复丢包不移动五秒截止、过期后的旧 generation 不能复活。

- [启动旧包处理后的检查](https://github.com/cyanrbt/walkbuddy/actions/runs/40878318461)的 Android 35 两轮通过，Android 36 在新会话已 LIVE 后又被锁屏通知停止。该原因仅从息屏接收器进入，与迟到通知相符，但没有原始广播发送时刻。[Android 广播说明](https://developer.android.com/develop/background-work/background-tasks/broadcasts)明确交付时机不保证，缓存进程可能延后接收。现在收到通知时核对当前屏幕与锁屏状态，只在仍息屏或锁定时停止；离屏 onStop 仍无条件停止。新增亮屏解锁后重放内部接收器回归，真实息屏停止流程仍保留。

以上是 x86_64 模拟器结果，不证明 ARM64 真机稳定性、识别准确率、TalkBack、AR 深度或实际耗电。版本为 0.4.9 / 21，包名/固定签名不变；更多设备场景见[实机测试](实机测试.md)。

## 时间戳问题与修复边界

[修复前的 Android 35/36 运行](https://github.com/cyanrbt/walkbuddy/actions/runs/40862893581)失败。下载的计时日志显示 `elapsedRealtimeNanos - SENSOR_TIMESTAMP` 分别约为 -4.884ms / -3.495ms（35）和 -16.237ms（36）；与 `System.nanoTime` 比较也为负值。这说明元数据在其时间戳之前返回，并非超过 1200ms 的旧帧。

[AOSP 元数据定义](https://android.googlesource.com/platform/system/media/+/c61e164fe52ee63bc3d9be8a6207e9a6719a9c1c/camera/docs/metadata_properties.xml)规定 REALTIME 采用 elapsedRealtimeNanos 对应时基；UNKNOWN 不假定同一时间原点。[AOSP 虚拟传感器实现](https://android.googlesource.com/platform/hardware/google/camera/+/9f9afdd93b8f6e3e1e30855f4214885d830ec85d/devices/EmulatedCamera/hwl/EmulatedSensor.cpp)把下一次采集时刻设为帧结束时刻，并有在休眠前提前返回结果的分支。该机制与实测现象一致；这是对公开源码和日志的对应推断，没有核对云端系统镜像的逐字源码版本。

`CameraFrames` 对最多提前 33,333,334ns 的元数据等待到相应时间后重验，不立刻算作新鲜帧。心跳仍使用最初收到回调的时刻，不把等待完成时刻当成新采集；原先已过期的会话不能恢复。每个预览至多一个待校验元数据任务，不保留图像，停止与故障取消；旧 generation 忽略。1200ms 采集/显示、5000ms 启动和 1500ms 分析截止保持不变，超过预算或迟到仍失败，AR 后端不使用此路径。
