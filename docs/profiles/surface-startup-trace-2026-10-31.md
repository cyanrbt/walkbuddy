# Surface 专项之后的预览启动采证

## 要解释的实际失败

主分支 `a4bbb53` 的 [Surface 专项 41172338642](https://github.com/cyanrbt/walkbuddy/actions/runs/41172338642) 中，API 35 首次问题快照的采集/显示龄为 1436/1420ms，亮度请求墙钟耗时 1383ms、线程 CPU 为取整后的 0ms，交付等待 11ms。[完整原始附件核对与首份问题快照](brightness-v038-main-first-expiry-2026-10-31.json)保留。这证明发生了画面过期，尚不能确定等待的是 GPU、RenderThread、调度还是其他工作。

下一次 [41173728712](https://github.com/cyanrbt/walkbuddy/actions/runs/41173728712) 的 API 35 冻结像素子检查通过，但随后首页 `focus=false`、再后屏幕 `interactive=false`，整轮失败；不把它归为同一次亮度停顿。独立 [Android 15/16 普通检查](https://github.com/cyanrbt/walkbuddy/actions/runs/41173728725)和 [v0.4.38 正式发布](https://github.com/cyanrbt/walkbuddy/actions/runs/41172338591)成功，不能覆盖这两个失败。

原系统轨迹只覆盖四轮 PiP 恢复，没有包含失败之前的 Surface 专项。查看实际脚本还发现：专项后进入普通 UI 检查时，会重新安装应用 APK 和测试 APK。这两次安装可能影响进程和窗口状态，采证不能省略。

## 本轮改动

- 第一条轨迹在冻结生产者专项前启动 Perfetto，执行原有 32 组 Surface 像素比较、两组虚拟 Camera2 与两组 EGL 比较，再按原顺序重新安装同一批编译产出的两份 APK，然后运行原四轮 PiP 恢复。恢复阶段仍启用测试专用主线程和亮度阶段记录。
- 第二、三条轨迹仍只执行原恢复检查。三条记录明确标注场景，不能合并为同一工作负载的配对性能数据。
- 专项必须同时具有三项成功标记、进程退出成功且无失败标记；两次安装各需退出成功与 `Success`。前序失败时保留原始输出、部分超时输出及同一条轨迹，不启动恢复，不重试探针；后两条独立轨迹仍采集，整体仍失败。
- Perfetto 最长采集从 120 秒改为 240 秒，以包含专项 45 秒、两次安装各 30 秒、恢复 110 秒的命令上限。完成后仍立即停止，文件上限、丢失检查、确认退出和同文件摘要核验规则保持。每条附件保存实际配置及摘要。这个采证上限不是应用启动或画面时效门槛。
- 摘要分别显示场景、专项结果与两次安装结果；原四个受控停止标记、调度/线程数据、解析错误和数据完整性要求保留。

## 验证与范围

本地 `python3 -m unittest discover -s scripts/tests -v`：50 项通过，9.302 秒；包括前序操作确实处于同一条轨迹中、零退出码缺少标记仍失败、安装失败不得进入恢复、专项超时保留部分输出并清理自有进程、恢复失败不重跑，以及仅第一轮增加前序操作。合成测试不代表模拟器运行成功。

本轮仅改采证工具、配置、测试与文档，`app/src/main` 和 `app/build.gradle` 相对正式 `v0.4.38` 无差异，包名、签名和已发布 APK 不变；不生成重复版本。云端 Android 15/16 采证及普通检查结果待推送后取得，不提前称为通过或根因修复。没有新增实体设备、AR、TalkBack、帧率或功耗验收。
