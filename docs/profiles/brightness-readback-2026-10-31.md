# 亮度读回的缓冲与耗时

v0.4.36 候选的自然采集/显示间隔曾达到 1246ms，精确根因未定位，[首次原始记录](recovery-native-candidate-first-2026-10-31.json)保留。现有代码把亮度读回放在绘制之后的主线程任务中，每秒最多一次；分配 16×12 ARGB_8888 位图，再执行 192 次 `getPixel`，没有单独记录这部分的墙钟/CPU 耗时。本轮不修改 1200ms 画面截止、1000ms 分析样本截止或暗画面阈值。

## 官方实现参考

[Android 15 TextureView 源码](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/view/TextureView.java)的尺寸重载创建位图后调用目标位图重载；后者可复用目标，但复制失败时可能保留原内容。因此复用之前必须清空，避免把上一帧亮度误当作本帧。继续在主线程、绘制回调之外读回同一 TextureView，不替换为原始相机流或窗口合成图。

## 基线与验证计划

先在生产代码与 v0.4.36 完全相同的提交中采集原生基线：原有 32 组传感器方向/显示方向/窗口尺寸，记录 16×12 像素摘要、RGB 总和、位图大小及分开的复制/求和计时。旧函数作为冻结参考保留在测试包，结果只说明构造 TextureView 的对应操作，不是相机端到端时延或实体设备性能。

之后验证复用位图/像素数组、逐像素及总和一致、暗画面边界、复制失败不沿用旧亮度、不可用表面和关闭释放。并在实际相机路径补充读回任务和亮度复制的墙钟/CPU 记录，帮助区分排队、读回和分析阶段；新增记录不等同于已证明历史停顿根因。

## 实现与本地结果

亮度读回保持 16×12、显示纹理、阈值 1728、每秒频率及原有绘制外调度。每次先清空目标，再复制并以一次 `getPixels` 求和；未取得表面返回未取得值，复制异常仍停止预览。相机停止时 recycle 位图并清除工作区引用，手动重新开启创建新实例。稳态应用代码不再为每次亮度检查分配新位图，像素读取 API 从 192 次变为 1 次；保留一个最多 768 字节位图和 768 字节 int 数组，因此不宣称总内存/峰值降低，框架和 GPU 内部分配不在此范围。

读回计时只保留固定数量的数值，正常更新不生成快照；故障和大于等于 200ms 的慢任务才生成记录。墙钟/CPU 分开测量，当前任务、任务内亮度阶段及最近已完成任务在事件快照中标明；不同相机代次不能混写，旧任务结束不能覆盖新代次。超时判断不使用这些诊断值，所有旧截止继续独立生效。

本地 0.4.37 / 49 的 243 项 JVM 为 0 失败/错误/跳过，Lint 和应用/原生测试包构建通过，具体警告数见 [JSON](brightness-readback-2026-10-31.json)。增加代次隔离、执行中/完成时间、零/无效时间与冻结报告恢复的回归。原生候选尚待验证，不据主机构建宣布 Android 行为或性能已通过。

## 原版原生基线

[41145407736](https://github.com/cyanrbt/walkbuddy/actions/runs/41145407736) 两套十项全部成功，生产源码与 v0.4.36 相同，原始 ZIP 已完整下载核对摘要并重放，[32 组每套的样本](brightness-native-baseline-2026-10-31.json)保留。位图均为 768 字节，构造 TextureView 复制墙钟中位数 API 35 约 2292µs、API 36 约 1286µs；单独求和 CPU 中位数约 105µs/115µs。不能将不同 VM 的绝对时间外推实体设备或解释历史 1246ms 间隔。

## 原生验收范围

候选保留旧十项和全部图像/模型对照：32 组实际 TextureView 的 ARGB、RGB 总和与缓冲身份；18 组受控颜色/透明/阈值/部分复制/复制未执行/不可用/错误与关闭；四轮 A-B-B-A、每轮 2000 次的受控原生位图操作计时，不包括 GPU 或相机。计时不设“必须更快”断言，原始每轮值保留。

实际 Camera2 检查覆盖复用、受控读回异常、首个事件冻结执行中耗时、释放相机/工作区/轮询、不自动重启及手动开启后新实例与连续新帧。受控异常不证明历史 GPU 停顿根因。实体设备、GPU 阻塞、帧率、GC、温升与耗电仍需单独测量。
