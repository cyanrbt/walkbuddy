# 两来源提醒的共同冷却

参考 [Lookout 的无障碍设计说明](https://design.google/library/google-lookout-design-accessibility)对视觉、声音和触觉协同的重视，本轮核对基础识别与深度检测共用提醒通道的实际状态流；不采用或宣称 Lookout 使用相同策略。

## 已复现的问题

v0.4.25 中，各来源的 `AlertPolicy` 先决定并记下目标已经提醒，`DetectionFeedback` 随后才检查共同间隔。后一层拒绝后，来源仍留下已提醒记录，下一份新结果可能要等目标重复周期，而不是在共同间隔允许时重判。

七组新增业务回归先在未修改的原实现运行：六组失败，一组通过，日志 `7 tests completed, 6 failed`，构建因断言失败退出 1。修正后全部通过，完整 170 项 JVM 为 0 失败 / 错误 / 跳过；Lint 0 错误 / 22 警告，应用与原生测试包构建成功。

另从 `v0.4.25` 标签（`3a9456b6b49d5ef02f2c78bf1aa7305b7d1d92fc`）与修正工作树分别提取五个纯 Java 类，在独立目录以相同驱动编译和执行。用 100ms 步长继续提供有效结果，得到下表；[完整 JSON](feedback-cooldown-2026-10-30.json)保留类文件源码摘要、逐步布尔输出及当时内容。

| 构造事件（ms） | v0.4.25 首次允许第二来源输出 | 修正后 |
| --- | --- | --- |
| 基础在 600 提醒；深度 700/900 连续确认红色 | 4900 | 1600（距上次 1000） |
| 深度黄色在 400 提醒；基础 500/700 连续确认黄色 | 8700 | 3400（距上次 3000） |

这些是可重复的构造时钟、结果和应用输出资格，不是实际 AR 识别、真实振动/声音、端到端延迟或安全反应时间。红色画面本来就可在连续确认后显示，本轮修正的是提醒记账和后续输出。

## 最终规则

- 在更新来源/目标已提醒记录之前，同时检查来源、目标及共同间隔；仅允许应用发出提醒时才记账。
- 保留共同普通间隔 3000ms、红色 1000ms；来源普通间隔 3000ms、红色升级 1000ms；同一目标黄色/红色重复至少 8000/4000ms。连续确认、距离/风险、数据有效期与会话截止保持。
- 被共同间隔阻挡时不保存待发内容或增加定时器。后续只有新的有效结果仍确认目标时才重判，使用当前距离、名称与风险。
- 目标消失、降级、空结果、过期、停止与模式切换按当前状态处理，旧提醒不回放。clear 仍要求新确认并保留已有静默间隔；重复、未来和过期深度不能释放旧提醒。

七组新增回归覆盖红色间隔边界和当前距离、另一来源黄色、实际允许输出后的重复间隔、目标消失、clear、新鲜性/重复/未来输入及降级。独立 JVM 轨迹与 Android 原生探针分别验证纯业务输出和实际提醒控件，均不替代物理设备。

## 原生及发布

`LayoutProbe` 已编译新增三组构造时序：两来源红色等待、另一来源黄色等待、消失后重新确认。在原 30 种窗口/字号/主题中核对输出布尔值、当前详情和实际 `RiskAnnouncer` 控件；旧布局、相机、小窗、锁屏、字体、密集标签与风险颜色检查保留。云端结果完成后补记，不能把编译通过称为原生执行成功。

目标设备的振动是否发生、声音与系统朗读是否清晰、真实深度稳定性、近距离时序及厂商策略仍待[实体设备验收](../实机测试.md)。
